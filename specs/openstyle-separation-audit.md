# Openstyle Fork-Separation Audit

## Verdict

The shipped desktop app is Electron, the local server, and the workspace packages electron-vite actually compiles in (`@openstyle/server`, `@openstyle/utils`, `@openstyle/validations`, `@openstyle/sdk`, `@openstyle/stt`). It is identity-clean where it counts: bundle id, code signing, the GitHub auto-update feed, the container registry, and the MLX-runtime download URL all point at the fork owner's own `Maheidem/openstyle`, confirmed directly against `apps/electron/electron-builder.yml`, the installed app's own `app-update.yml`, and `Info.plist`. Two live ties to the original developers remain inside that same shipped app: the in-app plugin marketplace (`apps/server/src/routes/plugins.ts`) still recommends, and the fork's own release CI is still configured to publish, packages under the original `@freestyle-voice` npm scope with GitHub links back to their repo, and the on-device speech-recognition binary the app runs today was compiled and published by the original developers, never rebuilt from the fork's own account. Separately, and worse in plain severity terms, the app's local REST API ships with bearer-token authentication silently disabled and a wildcard CORS policy (confirmed against both source and the real installed binary), so any webpage the user has open, or any other process on the machine, can read the complete dictation history and install and execute arbitrary npm packages with zero authentication. A fourth cluster that looks alarming in the raw severity table, a full "Freestyle Cloud" HTTP client compiled into the same `@openstyle/utils` package the desktop app depends on, rated critical, is dead weight specifically inside the desktop build: it ships as bytes in `app.asar` because electron-builder copies the whole workspace package folder, but a full-text search of the actual installed app (main process, renderer, preload, and every other bundled package) found zero references to it anywhere outside its own package folder; its only live caller is `apps/mobile`. Mobile is where nearly the entire critical/high volume of this audit actually lives (a hardcoded Sentry DSN, Stripe billing, mandatory OAuth sign-in, live audio streaming to the original vendor's servers by default), and it is real, workspace-registered, CI-built source that has never once reached a released build from this fork.

**Which findings could not be verified, and why, stated plainly:**

- **461 of 606 findings** were never routed to a verifier in the first place. The parent audit's own design only sent a subset of findings (145) through adversarial verification; the remaining 461 were always intended as inventory-only, first-pass observations with quoted evidence and a file:line citation, not independently re-checked by a second agent. This is not a defect in this phase. It's how the audit was scoped from the start.
- **65 of 145 routed findings** were sent to a verifier, but that verifier's verdict could not be recovered. The known defect (the orchestrator joined verifier verdicts to findings by JS object identity, which did not survive the parallel-execution boundary) stranded every verdict in its agent's own transcript. This recovery phase re-parsed 113 agent transcripts, found exactly 80 that were verifier runs (matching the "80 verifier agents actually ran" premise), and extracted a valid `StructuredOutput` verdict from all 80. The other 65 verifier runs either aren't among those 113 transcripts or left no recoverable verdict; their findings revert to unverified, honestly, rather than being assumed correct.
- **80 findings (79 confirmed, 1 refuted)** now carry a real second opinion. Of the 79 confirmed, 31 had their severity corrected by the verifier (22 downgraded, 9 upgraded); this report uses the corrected severity throughout and flags every correction inline. The 1 refuted finding (`apps/electron/src/main/index.ts:2629`, an auto-update claim) is kept in this report and marked REFUTED rather than deleted, see §4.
- The join between recovered verdicts and findings (by file, line, and category) matched all 80 verdicts to exactly one finding each, with zero ambiguous or unmatched keys. The mechanical part of this recovery is sound.

An "unverified" finding in this report is not a weak finding. It carries the same quoted evidence and file:line citation as a confirmed one, and where this report's author had direct repo access to spot-check a specific unverified claim against current source, that is noted inline (see §4's ship-reachability note and §7's stale-documentation note). "Unverified" means no independent second agent re-derived it. It does not mean doubted.

## What actually ships vs what merely exists

This monorepo contains one shipped product and several things that merely live next to it. Getting this distinction right changes how every severity number below should be read. A critical finding in dormant source is a very different fact from a critical finding in what the owner's machine runs today.

**Reaches the owner's machine (the "shipped desktop surface," 263 findings, used throughout §4):**

`apps/electron` plus `apps/server` plus the workspace packages `apps/electron/package.json` actually depends on: `@openstyle/utils`, `@openstyle/validations`, `@openstyle/sdk`, plus `@openstyle/stt`, which ships transitively because `apps/server` depends on it directly. `electron-vite build` compiles all of this into `out/main/index.js` + `out/renderer/`; `electron-builder` packages that into `app.asar` per `apps/electron/electron-builder.yml` (verified directly: `appId: com.openstyle.app`, `publish: {provider: github, owner: Maheidem, repo: openstyle}`), matching the actual installed app's `app-update.yml` byte for byte. `packages/create-freestyle-plugin` (a scaffolding CLI for third-party plugin authors) and `packages/stt`'s sibling `packages/` directories are the only other `packages/*`; `create-freestyle-plugin` is **not** an `apps/electron` or `apps/server` dependency and does not ship.

**Ships conditionally, opt-in only (the plugin marketplace, 44 findings under `plugins/`):**

`plugins/audio-transcription`, `plugins/emoji`, `plugins/profanity-filter` are never bundled into `app.asar`, confirmed by the parent audit's asar listing (zero `plugins/*` paths in 27,912 files) and by `apps/server/src/lib/plugins/installer.ts`, which fetches a plugin from `registry.npmjs.org` only when a user clicks Install, or pings the registry automatically when the Plugins page is opened (`check-updates`, a real but disclosed background call). The marketplace mechanism itself, meaning the catalog data and the installer, is core shipped surface (`apps/server/src/routes/plugins.ts`, `apps/server/src/lib/plugins/installer.ts`) and is covered in full in §4. The plugin source directories themselves are covered as a compact appendix at the end of §4 rather than the full exhaustive treatment, since none scored above low/info and they only reach a machine on explicit user action.

**Dormant, exists in the monorepo, reaches no shipped artifact (199 findings: mobile, agent-skills, docs-specs):**

- **`apps/mobile`** (85 findings, §6). A separate Expo/React Native app, workspace-registered (`pnpm-workspace.yaml`'s `apps/*` glob) and actively built, typechecked, and gated in CI (`.github/workflows/build.yml` jobs `mobile` and `mobile-android`, both required merge gates, both green on the latest run per `gh run view`). It is not bit-rotted. CI touches it on every push. But `apps/electron/package.json` has zero reference to it, the desktop build pipeline never imports it, `installed_app_contains_mobile` came back negative (full-content grep of the extracted `app.asar`: zero matches for `mobile`, `expo-router`, `react-native`, `@sentry/react-native`, `com.freestylevoice.app`), and no workflow in this repo ever runs `eas build`/`eas submit`/`expo publish`. Its own `app.json`/`eas.json` still name the original developers' Expo owner, Sentry org, and Apple Developer Team, accounts the fork owner does not control, which is itself evidence no one has attempted to ship it from here.
- **`.agents/skills/*`** (76 findings, all info/low). Vendored third-party AI-coding-assistant reference packs (Vercel React/React-Native best-practices, shadcn), introduced in the same commit that added `apps/mobile`. Zero Freestyle branding; the audit's own note confirms "this directory's provenance is Vercel, not Freestyle." Not itemized further in this report: noise, not signal, for a fork-separation question.
- **`specs/*.md`, `.lore.md`, `README.md`, etc.** (38 findings). Internal documentation, never bundled into any shipped artifact. Two specific high-severity claims sourced from `.lore.md` turned out to describe a superseded, pre-rebrand state of the code rather than current reality; see the callout in §7.

**The one correction that matters most for reading §4 correctly:** four of that section's critical findings and several of its highs are the compiled "Freestyle Cloud" HTTP client (`packages/utils/src/cloud-client.ts`, `cloud.ts`, `cloud-errors.ts`, and the `package.json` export subpath that makes it importable). The verifier correctly confirmed this code is real and live, but "live" there means live for its one actual caller, `apps/mobile`. This report's author independently re-verified desktop-reachability directly against the real installed app: extracted `/Applications/Openstyle.app/Contents/Resources/app.asar` in full (342 MB, `@electron/asar` v3.4.1), and grepped every file in `out/main`, `out/renderer`, `out/preload`, and every other `node_modules` package for `CloudAuthError`, `createCloudClient`, and `CloudUsageLimitError`. Zero matches outside `node_modules/@openstyle/utils/{src,dist}` itself: the compiled `dist/cloud.js`/`dist/cloud.cjs` files physically exist inside `app.asar` (electron-builder copies the whole workspace package folder, not just what's imported), but nothing in the actual bundled desktop code ever calls into them. A second, related check: `packages/validations/src/cloud-config.ts`'s `orderBySuggestedLanguages`/`resolveLanguageOptions` functions *are* bundled into the shipped renderer (`out/renderer/assets/index-CY9EsQf-.js:4393`), but in the compiled, minified output the function body is `function orderBySuggestedLanguages(options, suggested, getCode, pinnedFirst) { return [...options]; }`. Every parameter except `options` is dead, unused. The desktop build ships the shape of a cloud-language-ordering feature with the actual ordering logic compiled away to a no-op passthrough. Every affected row in §4 is flagged individually; treat "reachable: active" in those rows as "active for apps/mobile," not "active in the desktop app you run."

Severity distribution for the true shipped core: **4 critical, 19 high, 17 medium, 131 low, 92 info** (§4 covers critical through low in full; info is summarized).

**Full reconciliation of all 606 findings by surface**, so every row in the underlying data is accounted for somewhere in this report: desktop-electron (140) + server (87) + the shipped slice of shared-packages (36) = 263 core shipped (§4); plugins (44, §4 appendix); mobile (85, §6); agent-skills (76, mentioned above, not itemized); docs-specs (38, §7's callout plus §8's brand table); installed-app (23) + runtime-machine (13) = 36 (§5); build-ci (15, §7); the remaining 14 shared-packages findings (`packages/create-freestyle-plugin`) plus the 35 "other" findings (`templates/`, `LICENSE`, `knip.jsonc`), 49 total dev-tooling and scaffolding, covered in §8's brand inventory rather than a dedicated section, since none ship and none scored above medium. 263 + 44 + 85 + 76 + 38 + 36 + 15 + 49 = 606.
